# 基于RAG和低GI库的糖尿病饮食管理小程序 — 技术方案

## 一、项目背景与痛点

我国 2 型糖尿病患者数量庞大，饮食管理是血糖控制的核心环节。但患者在日常饮食中面临几个实际困难：

1. **不知道该吃什么**：对食物的 GI 值、糖分含量缺乏了解，难以判断哪些食物适合自己
2. **难以坚持记录**：传统的饮食记录需要手动输入食物名称和重量，门槛高、易放弃
3. **建议不够个性化**：通用的控糖建议没有结合患者的血糖数据、饮食偏好和并发症情况
4. **信息真假难辨**：网络上的饮食建议质量参差不齐，患者难以判断可信度

本项目的核心思路是：**用自建的低 GI 食物知识库做数据底座，用大模型做自然语言交互，让患者用对话的方式就能获得专业、个性化的饮食建议。**

## 三、核心功能设计

### 3.1 AI 健康问答（已实现）

用户用自然语言提问（如"我血糖偏高，早餐能吃面条吗？"），系统调用 DeepSeek Chat API，通过 system prompt 限定角色为"专业糖尿病健康顾问"，返回简洁、包含关键医疗建议的回答。

关键实现：`pages/qa/qa.js` → `callDeepSeekAPI()`

### 3.2 低 GI 食物知识库（已实现）

自建三个知识库文件：

| 知识库 | 规模 | 字段 |
|--------|------|------|
| `food_nutrition.csv` | 114 种食材 | 食物名称、类别、糖分、蛋白质、碳水、膳食纤维、GI 值 |
| `food_disease_relations.csv` | 107 条 | 食物名称、疾病名称、关系类型（推荐/限制等） |
| `food_substitute.csv` | 23 条 | 原食物、替代食物、替代原因（如"白面条→荞麦面，低GI替代"） |

另有 Excel 版本（`data/` 目录）：低 GI 食物营养成分知识库.xlsx、控糖食谱案例库.xlsx。

### 3.3 饮食记录（前端逻辑完整）

- 记录每餐食物和份量
- 今日糖分统计 + 进度条
- 周报展示
- 数据当前为前端模拟（`app.js` → `globalData.dietRecords`）

### 3.4 AI 营养师（规则演示）

当前为基于关键词的 if-else 规则推荐（如"面条→荞麦面"、"米饭→糙米"），完整方案为大模型生成个性化食谱（详见 Issue #3）。

## 四、RAG 检索增强方案设计（作品报告核心，待落地）

作品报告中设计了"三级增强链路"，目标是让大模型的回答受本地知识库约束，减少幻觉、提升专业性：

### 第一级：结构化知识图谱检索

- 将 `food_nutrition.csv`、`food_disease_relations.csv`、`food_substitute.csv` 导入 Neo4j
- 构建实体：食物、营养成分、疾病、替代食物
- 构建关系：包含、推荐、禁忌、替代
- 用户提问时，先通过 Cypher 查询从知识图谱中检索相关实体和关系

### 第二级：非结构化 RAG 检索

- 将控糖食谱案例库向量化（Embedding）
- 用户提问时，检索语义相似的食谱案例
- 作为上下文补充给大模型

### 第三级：大模型生成

- 将前两级检索到的结构化数据 + 非结构化案例作为上下文注入 Prompt
- 要求大模型基于检索结果生成回答，不得编造知识库中不存在的信息
- 回答中引用具体的食材 GI 值、营养成分等数据

> 这三级增强链路是本项目的核心创新点，但当前原型仅实现了第三级的"直接问答"，前两级检索尚未落地代码。详见仓库 Issue #1。

## 五、已知问题与改进方向

当前版本为竞赛参赛原型，以下功能为模拟或待实现，详见仓库 Issues：

1. **RAG 检索增强未落地**：当前 AI 问答为直接调用大模型，未结合本地知识库（Issue #1）
2. **食物拍照识别为模拟**：上传图片后返回硬编码结果，需升级为多模态大模型真实识别（Issue #2）
3. **AI 营养师为规则推荐**：需升级为大模型生成个性化食谱（Issue #3）
4. **知识图谱未实现**：Neo4j 知识图谱为设计方案，未落地代码（Issue #4）
5. **数据为前端模拟**：饮食记录、健康监测数据存在 `globalData` 中，未接入云数据库

## 六、技术栈

- **前端**：原生微信小程序（WXML + WXSS + JavaScript）
- **AI**：DeepSeek Chat API（`deepseek-chat` 模型）
- **知识库**：CSV + Excel（自建低 GI 食物营养成分库）
- **设计方案**：RAG 检索增强 + Neo4j 知识图谱（详见作品报告）
- **数据存储**：当前为前端模拟，后续可接入微信云开发数据库
